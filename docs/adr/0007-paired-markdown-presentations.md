# ADR 0007: связанные представления исходника и Markdown

Дата: 2026-11-04. Статус: принято, реализация по этапам.

## Контекст

Markdown уже имеет переносимую семантическую модель, формулы, Mermaid и
терминальный renderer. Режим внутри редакторской вкладки не выражает нужный
жизненный цикл: после закрытия редактора пользователь должен сохранить
просмотр, затем прочитать изменившийся файл заново.

Наличие просмотра не означает наличие открытого редактируемого документа.
Нельзя сохранять editor engine, history или невидимое editing view только
ради отрисовки или записи снимка. Общие контракты должны подходить Android
и desktop и сохранять Java 17 baseline.

## Решение

### Реестр и идентичность

`EditorWorkspace` остаётся единственным владельцем порядка представлений,
выбора и membership открытых документов. В `editor-contract` добавляются
`PresentationId` и `PresentationGroupId`, независимые от `DocumentId` и
редакторского `ViewId`.

Generic запись представления содержит ID, группу, attachment frontend и
явный binding: `Editing(document, viewId)` либо `Projection`. Вторая форма
не содержит ссылки на документ или engine. Существующие коллекции editing
views становятся проекциями того же immutable состояния workspace. Второго
изменяемого списка вкладок и второго указателя выбранного документа нет.

Workspace ничего не знает о Markdown. Правило пары реализует TUInk:
`SourceTab` содержит редакторское представление, `PreviewTab` — только своё
состояние и связь. В существующем приложении имя `EditorTab` может остаться
именем типа source; различие source и preview обязательно в типах.

Одна группа содержит source слева и не более одного preview справа. Открытие
новых документов вставляет группу целиком. Навигация выбирает представления,
включая обе части пары. Editing-only коллекции используются для dirty,
recovery и массовых команд и не считают preview редакторским view.

Для изменения порядка, вставки source и замены live binding на frozen
предусматривается одна подготовленная публикация membership и attachments.
Все проверки и выделение коллекций заканчиваются до изменения владения.
Транзакция может retire не более одного editing view: backend detach способен
подготавливать replacement engine, поэтому произвольный bulk detach нельзя
обещать атомарным без отдельного backend contract. Этой границы достаточно
для закрытия source и повторного открытия пары.

### Жизненный цикл preview

Binding feature имеет два состояния:

- `LiveSource(documentId, viewId)`: разрешение через workspace, без владения
  сессией редактора;
- `ClosedSnapshot`: полный immutable исходник и отдельный получатель
  сохранения; ссылок на `EditorDocumentSession`, `TuiDocumentSession`, engine
  и прежнюю editing history нет; история последующих внешних изменений
  принадлежит frozen subject.

ID preview и группы сохраняются при обычном повторном открытии. Новая сессия
редактора получает новые ID. Поколение связи растёт при freeze, повторном
открытии и замене ресурса. Worker receipts проверяются по presentation ID,
поколению, исходнику и operation token.

Ctrl+P из source создаёт/активирует preview, из live preview активирует
существующий source. Из closed preview команда запускает чтение файла с диска.
Если frozen subject несохранён или имеет внешнюю Undo/Redo history, повторное
открытие не relink/retire этот subject: Source добавляется независимо с новым
document/group ID, а прежние Preview, текст, история и recovery остаются.
При уже открытом владельце ресурса выбирается тот Source без замены frozen
вкладки. Пользователь получает явное сообщение об отдельных вкладках.
Обычные команды вкладок работают с тем же registry. Закрытие preview не
закрывает source. Закрытие source проходит Save / Discard / Cancel и завершает
редакторскую сессию даже при оставшемся preview.

### Полный снимок

В `editor-contract` используется immutable envelope `FrozenDocumentSource`:
`DocumentSnapshot`, `DocumentFileMetadata`, `ResourceBinding`. Метаданные
должны соответствовать числу строк. Последняя пустая строка сохраняет
завершающий перевод строки; TeX, Mermaid, tabs и trailing spaces сохраняются
из raw snapshot, а не восстанавливаются из AST или Copy projection.

Owner захватывает текст, формат и binding до отправки worker, без yield между
чтениями. Приём результата привязывает именно этот envelope к результату.
Изменение только формата или binding не требует повторного parse, но обновляет
соответствующие captured данные на owner. SourceMap продолжает описывать
идентичность и ревизию текста.

При закрытии source выбирается последний принятый preview envelope. Если
preview ещё ни разу не был построен, используется исходник, захваченный при
создании preview. Незавершённый worker не может заменить этот снимок после
freeze. Явно завершённый Save As обновляет resource/baseline пары, сохраняя
формат и текст выбранного снимка. Наличие более новых правок в закрытом source
не даёт права незаметно заменить уже показанный снимок.

Подготовка снимка и admission бюджета завершаются до retirement source.
При отказе редактор, preview и прежняя membership остаются на месте. После
Discard неизменённый frozen snapshot не входит в dirty/recovery registry, а
закрытие оставшегося preview не повторяет вопрос об уже закрытом source.
Последующий Keep внешней версии или Undo может оставить несохранённый frozen
текст: он уже участвует в dirty-индикации, close/quit guards и recovery. Для
внешних изменений frozen subject хранит собственную историю текущего сеанса;
прежняя история закрытого editor не удерживается. Recovery использует текущую
схему текста/формата/дискового baseline, без истории Undo и Preview layout.

### Открытие и сохранение

Повторное открытие использует существующий async storage pipeline, проверку
aliases и admission. Уже открытый dirty владелец ресурса остаётся владельцем:
его текст не перечитывается и не заменяется. Preview переносится к нему;
при коллизии используется существующая пара без второго preview. Ошибка
чтения сохраняет выбранный preview, снимок, поиск и положение.

`DocumentIoCoordinator` получает общий save-subject port. Live adapter
сохраняет существующее backend поведение. Frozen subject владеет только
immutable исходником, binding, поколением, историей принятых внешних изменений
и собственным временем жизни I/O.
Он не создаёт `EditorDocumentSession` или engine. Inspection, authorization,
receipt validation, cancellation и неизвестный результат публикации остаются
одним storage protocol; отдельного `Files.write` пути нет.

Save из live preview сохраняет последний live буфер, даже если layout ещё
старый. Save из closed preview сохраняет raw frozen source. Save As обновляет
имя и reopen target только после подтверждённого receipt. Pending write имеет
собственный token и может завершаться независимо от видимости вкладки;
поздняя публикация не меняет новую привязку preview или соседний документ.

Автоматический Save → Save As при недоступном файле не утверждён и не входит
в реализацию. Доступны явный Save As и обычные ошибки/конфликты storage.
Недоступность ресурса не подменяет конфликт версии.

### Видимость и память

В кадре показано одно представление. Source frame требует редакторскую
сессию; preview frame строится из immutable layout и общего chrome, без
фиктивного редактора под ним. Общие меню, диалоги и focus policy используются
повторно. Input выбирает получателя по типу представления до обращения к engine.

Активация preview немедленно запрашивает актуальный live source. Suspend
отменяет consumer request, освобождает тяжёлый layout и индексы, сохраняя
исходник, semantic/source anchors и лёгкое состояние поиска. Suspend не
является изменением типа вкладки и не вызывает закрытие документа.

Один сервис окна ограничивает worker pool, очередь, parse cache и общий
бюджет retained snapshots/models. Shared immutable blocks учитываются без
обязательной материализации строк. Отказ admission не удаляет принятый
снимок и не создаёт скрытый editor. Скрытые запросы не вытесняют активный.

## Проверка решения

Для каждого перехода проверяются registry/order/selection, document ownership,
raw snapshot и формат, dirty/recovery, отмена и stale callbacks. Обязательны
обычные клавиши вкладок и реальные modal/save сценарии, Java 17/D8/R8,
JVM/native smoke с формулами и Mermaid. Нагрузочные paste timeouts baseline
оцениваются отдельно и не скрываются увеличением лимитов.
